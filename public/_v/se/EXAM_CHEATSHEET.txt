PRACTICAL 1 - SDLC STUDY
------------------------------------------------------------------------------
7 phases ane output (j project aave tema same phases lakhvana):
  1 Planning              -> feasibility (technical/economic/operational), cost+time estimate, risks | Project plan, feasibility report
  2 Requirement Analysis  -> stakeholders sathe vaat, requirements lakhvi + check | SRS
  3 Design                -> architecture, DB (ER), DFD, UML, UI screens | HLD + LLD, UI designs
  4 Implementation        -> coding, coding standards, code review, Git | Source code
  5 Testing               -> unit, integration, system testing, bug fix | Test cases, test report, bug reports
  6 Deployment            -> server par mukvu, DB + gateway setup, training | Live system, user manual
  7 Maintenance           -> bug fix, navi features, update, backup | Patches, new versions
Models: Waterfall (clear/fixed requirements), Iterative/Incremental (working version jaldi),
        Spiral (high risk - dar loop ma risk analysis), V-Model (darek dev phase ni sathe test phase),
        Agile/Scrum (requirements vare vare badlay, sprints).
Benefits: clear structure, defined output darek phase no, early errors = ocho cost, saru communication, time par quality product.

PRACTICAL 2 - SRS (Requirements Specification)  -> aa headings j lakho
------------------------------------------------------------------------------
1. Introduction      : Purpose, Scope, Intended audience, Definitions (SRS, FR, NFR, OTP...)
2. Overall Description: Product perspective, Product functions, Operating environment, Constraints, Assumptions, User classes (table)
3. Specific Requirements
   3.1 Functional (table: ID | Requirement | Priority)   -> "The system shall ..."  FR-1, FR-2, ...
   3.2 External interface: User / Hardware / Software / Communication interface
   3.3 Non-functional: Performance, Security, Reliability, Usability, Portability, (Responsiveness)
Tip: darek requirement measurable hovi joie ("page 3 second ma load thay", "OTP 5 minute ma expire").

PRACTICAL 3 - USE CASE DIAGRAM
------------------------------------------------------------------------------
Steps: 1) Actors shodho (primary = manus; secondary = external system jem payment gateway).
       2) Darek actor na use cases (verb + noun: "Enroll in Course").
       3) System boundary (motu rectangle, upar system nu naam), use cases ellipse ander, actors bahar.
       4) Actor <-> use case ne seedhi line (association).
       5) <<include>>  : base use case ma sub-use-case HAMESHA chale (Enroll in Course --> Make Payment), dashed arrow base thi included taraf.
          <<extend>>   : optional/special condition (Login <-- Forgot Password), dashed arrow extending thi base taraf.
          Generalization: hollow-triangle arrow (Admin ek type no User).

PRACTICAL 7 - DFD (Data Flow Diagram)
------------------------------------------------------------------------------
Level 0 (Context): system = ek j process (0), badhi external entities, darek arrow par DATA nu naam.
Level 1: process 1.0, 2.0, 3.0 ... + data stores D1, D2 ... + entities. Level 0 na darek input/output Level 1 ma hova joie (BALANCING).
Rules: process ma input ANE output banne hova joie | data store <-> data store ke entity <-> entity seedhu nahi |
       arrow par data nu naam (action nahi) | process naam = verb ("Enroll and Pay").
Symbols: process = circle/rounded box | entity = rectangle | data store = open-ended rectangle (D1 Users)
Examples: Figures_and_Diagrams\P07_DFD_level0.png, P07_DFD_level1.png

PRACTICAL 9 - TEST COVERAGE + CYCLOMATIC COMPLEXITY   (code: Practical_09_...)
------------------------------------------------------------------------------
V(G) = E - N + 2   (E = edges, N = nodes)   athva   V(G) = P + 1   (P = decision/if ni sankhya)
Aa function ma: 3 if -> V(G) = 4  => 4 independent paths => ochha ma ochha 4 test cases.
Coverage:  Statement = executed statements / total | Branch = executed branches (true+false) / total | Path = executed paths / V(G)
Navu function aape to: (1) control flow graph dorvo (darek statement/decision = node), (2) V(G) kado,
(3) darek path mate 1 test case (input + expected), (4) coverage percent kado.
Python run: python practical9_coverage.py   (function badli ne navi problem pan chale che)

PRACTICAL 10 - TEST SUITE (4 techniques)   (code: Practical_10_...)
------------------------------------------------------------------------------
Equivalence Partitioning : input ne valid + invalid class ma vahecho, darek class mathi 1 value.
Boundary Value Analysis  : range [min, max] mate  min-1, min, min+1, max-1, max, max+1   (price 1..50000 -> 0,1,2,49999,50000,50001)
Decision Table           : conditions na badha combination (Logged in? Payment? Seats?) -> darek rule mate result.
Error Guessing           : developer je bhuli jay: string, None, True, negative, decimal, empty.
Test case format: ID | Description | Input | Expected | Actual | PASS/FAIL
Run: python test_suite.py  (course_module.py same folder ma)

PRACTICAL 11 - LOGIN / REGISTRATION / OAUTH TESTING   (code: Practical_11_...)
------------------------------------------------------------------------------
Test groups: Sign Up (valid, duplicate email, invalid email/name, weak/short password, confirm mismatch, password hash thay che)
             OTP (correct, wrong, expiry 299/300 s, 3 wrong attempts, resend)
             Login (correct, wrong password, unknown email same message, case-insensitive, not verified, lock after 5 fails, unlock after 15 min)
             Session (fake token, valid 1799 s, expire 1800 s, logout)
             Google OAuth 2.0 (state hamesha check = CSRF, state/code ek j var, code 5 min ma expire, user duplicate na thay)
OAuth 2.0 flow (authorization code): User "Continue with Google" -> app state banave -> Google login + consent -> Google code aape
             -> app code + state check kare -> code ne token/profile mate exchange kare -> app session banave.
Run: python test_auth.py  (learnsphere_auth.py same folder ma)
